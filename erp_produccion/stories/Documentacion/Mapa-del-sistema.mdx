#### Comportamiento importante de administración

- **Dashboard:** el componente de analítica consulta `GET /api/admin/analisis`; también puede cargar reportes dinámicos con `GET /api/reportes/esquema` y `POST /api/reportes/dinamicos`.
- **Exportación:** la selección de tablas se genera a partir de las tablas disponibles para exportación; no representa una lista fija de columnas en esta documentación.
- **Carga de órdenes:** la pantalla acepta un archivo para `POST /api/ordenes/subir`. El parser de esa ruta lee contenido delimitado por `;` y encabezados, e inserta cada orden en `ordenes_produccion` y `admin_costura_ordenes`.
- **Manuales:** actualmente los formatos aceptados por el selector son `.pdf`, `.png`, `.jpg` y `.jpeg`. La relación entre nombre de archivo y producto depende de la regla de código que aplica el módulo.
- **Catálogo de tiempos:** la búsqueda de la UI filtra por código en las páginas ya cargadas; usa **Cargar siguientes 50 productos** para incorporar más filas antes de concluir que un código no existe.

| URL / archivo | Propósito | Datos y acciones principales |
| --- | --- | --- |
| `/admin_costura` — `app/admin_costura/page.tsx` | Portada del área de costura. | Recupera el usuario con `/api/me` y presenta el panel del área. La página actual es una portada informativa. |

| `/admin_costura/operadores` — `app/admin_costura/operadores/page.tsx` | Disponibilidad y carga por operador. | Habilita o deshabilita operadores, muestra vencimiento de disponibilidad y asignaciones no terminadas. Al entrar, ejecuta el ciclo automático de asignación. |

No es la pantalla de cronometraje de corte. |
| `/admin_costura/papelera` — `app/admin_costura/papelera/page.tsx` | Recuperación de órdenes retiradas. | Lista órdenes en papelera y las restaura a `admin_costura_ordenes`. |

#### Ciclo de una orden de costura

1. La orden de producción se importa y queda disponible en la cola de `admin_costura_ordenes`.
2. El área de corte la consulta, inicia el corte y al finalizar registra el fin y estado cortado.
3. La disponibilidad de operadores y el ciclo automático crean o reanudan filas en `admin_costura_asignaciones`.
4. El operador ve la asignación y abre una sesión real de costura.
5. El histórico de órdenes cortadas agrega el estándar unitario por familia y calcula el estimado de la cantidad completa.

Los estados y las cantidades son distintos: `cantidad` es la cantidad original de la orden; `cantidad_asignada` es el subconjunto entregado a un operador; `total_asignado` suma asignaciones para mostrar el avance.

### Operador

| URL / archivo | Propósito | Datos y acciones principales |
| --- | --- | --- |
| `/operador` — `app/operador/page.tsx` | Ejecución de la asignación. | Consulta sesión y asignaciones propias; muestra OP, producto, cantidad, manual asociado, cronómetro y órdenes pausadas. Inicia costura y termina la asignación. |

### Claves físicas y uniones de aplicación

Solo tres claves foráneas están declaradas en los DDL recibidos:

| Clave foránea | Comportamiento |
| --- | --- |
| `sesiones.usuario_id → usuarios.id` | Al borrar el usuario, MySQL elimina sus sesiones (`ON DELETE CASCADE`). |
| `operadores_disponibilidad.usuario_id → usuarios.id` | Al borrar el usuario, MySQL elimina su disponibilidad (`ON DELETE CASCADE`). |
| `admin_costura_ordenes_espera.orden_id → admin_costura_ordenes.id` | Al borrar la orden, MySQL elimina la fila de espera (`ON DELETE CASCADE`). |

Las consultas también enlazan `admin_costura_cortes.orden_id` con órdenes/asignaciones y `admin_costura_asignaciones.id_operador` con usuarios, pero esos vínculos **no tienen FK declarada** en los DDL recibidos. `operador_tiempos_costura.id_asignacion` es `BIGINT`, mientras `admin_costura_asignaciones.id` es `INT`; el DDL no declara FK entre ellos. El código permite sesiones históricas con `id_asignacion` nulo.

| Relación usada por la aplicación | Criterio |
| --- | --- |
| Orden de costura → corte | `admin_costura_cortes.orden_id = admin_costura_ordenes.id`. |
| Corte → asignaciones | `admin_costura_asignaciones.orden_id` se compara con el `orden_id` del corte; el código mantiene compatibilidad con cortes antiguos donde se usa el `id` del corte. |
| Asignación → operador | `admin_costura_asignaciones.id_operador = usuarios.id`. |
| Tiempo real → asignación | `operador_tiempos_costura.id_asignacion = admin_costura_asignaciones.id`; también hay recuperación por `op`, operador y cantidad para sesiones históricas sin ID. |
| Petición → métrica | Coincidencia de `codigo` exacto o por los primeros siete caracteres contra `productos_tiempos.cod_proceso`; no es FK. |
| Manual → producto | Coincidencia de código relacionado o nombre de archivo en la lógica de consulta; no es FK. |

### Diferencias de nombres y columnas que conviene atender

- El DDL confirma tablas en minúsculas (`usuarios`, `sesiones`). Algunas rutas escriben `Usuarios` y `Sesiones` con mayúscula inicial. En MySQL, la sensibilidad a mayúsculas depende del sistema y de `lower_case_table_names`; se recomienda normalizar el código a minúsculas para evitar errores al desplegar en Linux.
- `admin_costura_ordenes` tiene `UNIQUE KEY (op)`; `ordenes_produccion` no la declara. `productos_tiempos.cod_proceso` también es nullable aunque tenga índice único: MySQL permite múltiples `NULL` en un índice único.
- La tabla `admin_costura_tiempos_corte` no se incluyó en los archivos. El código escribe `orden_id` y `estado`; se necesita su DDL para completar la referencia.
- `admin_costura_cortes`, `admin_costura_asignaciones` y `operador_tiempos_costura` copian datos de la orden para el flujo operativo y no declaran FK entre sí. Mantener consistentes esos valores depende de la lógica de aplicación.

## 4. Ejemplo documentado de lectura y escritura

### Estimar una orden

Supongamos producto `155-20000-DGY`, 9 piezas y un registro de familia con `t_costura = 2100`.

```text
prefijo consultado     = "155-200"
estándar unitario      = 2100 segundos
total                  = 9 × 2100 = 18 900 segundos
valor mostrado         = ceil(18 900 ÷ 60) = 315 minutos
```

La API de órdenes usa `tiempoCosturaPorPrefijoSql('c')` para agregar `tiempo_base`; la página multiplica por cantidad y divide el total entre 60. Para el cronómetro real, la ruta de inicio inserta una sesión y la ruta de fin suma `TIMESTAMPDIFF(SECOND, fecha_inicio, NOW())` a `tiempo_segundos`.

### Aprobar un tiempo faltante

```json
{
  "peticion_id": 812,
  "modelo": "155-200",
  "nombre": "Modelo base",
  "codigo": "155-20000-DGY",
  "nombre_secundario": "Silla de ejemplo",
  "costura": "Costura",
  "tiempo": "2100"
}
```

`POST /api/productos/peticiones/aprobar` escribe `codigo` en `cod_proceso`, `nombre_secundario` (o `nombre`) en `descripcion`, `costura` en el campo de operación y `tiempo` en `t_costura`; luego cambia el estado de la petición a `atendido`.

## 5. Observaciones técnicas derivadas del esquema

1. Los trece archivos permiten documentar tipos, índices y claves foráneas de las tablas incluidas. Falta el DDL de `admin_costura_tiempos_corte`, que sí aparece en las rutas de corte iniciadas desde la papelera.
2. El código mezcla referencias `Usuarios`/`usuarios` y `Sesiones`/`sesiones`, mientras el DDL define nombres en minúsculas. Comprueba `lower_case_table_names` en producción; se recomienda normalizar las consultas a minúsculas para evitar diferencias entre sistemas.
3. La subconsulta compartida de tiempos excluye `N/A`, `NA` y `N/D`; el endpoint de peticiones verifica que el valor de costura no esté vacío y que el tiempo sea positivo, pero no excluye esos literales. Conviene unificar esa validación para evitar que una petición se marque atendida mientras la consulta de estimación ignora el registro.
4. `admin_costura_ordenes` y `admin_costura_cortes` duplican datos de la orden para el flujo operativo. Las tablas de cortes, asignaciones y tiempos reales no declaran FKs entre ellas en el DDL recibido; las consultas dependen de que los identificadores y datos copiados permanezcan consistentes.
5. `productos_tiempos.cod_proceso` permite `NULL` aunque tenga índice único. MySQL permite más de un `NULL` en ese índice; la API de catálogo exige código no vacío al crear o modificar productos.

El dump original no incluye `modelo`, `nombre`, `linea` ni `tiempo_total_costura`. Las migraciones versionadas agregan esos campos; aplícalas en orden antes de desplegar la versión actual. La carga importa `tiempo_total_costura` como viene en el archivo, y si está vacío lo conserva como `NULL`.

## 6. Cobertura del esquema entregado

Los archivos recibidos documentan estas trece tablas: `admin_costura_asignaciones`, `admin_costura_cortes`, `admin_costura_ordenes`, `admin_costura_ordenes_espera`, `admin_costura_papelera`, `manuales_produccion`, `operador_tiempos_costura`, `operadores_disponibilidad`, `ordenes_produccion`, `peticiones_tiempos`, `productos_tiempos`, `sesiones` y `usuarios`.

Los SQL se exportaron por tabla, no como un DDL consolidado de toda la base. El archivo de `productos_tiempos` contiene filas además de la definición; esta documentación solo utiliza su `CREATE TABLE`. Para cerrar el inventario de objetos que usa la aplicación, falta recibir la estructura de `admin_costura_tiempos_corte` y cualquier otra tabla no incluida en esos archivos.
