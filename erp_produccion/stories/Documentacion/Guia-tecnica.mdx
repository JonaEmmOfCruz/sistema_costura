# Guía técnica

## 1. Alcance y convenciones

Esta guía describe cómo fluye la información entre las pantallas de costura, las API y MySQL. Está dirigida a desarrollo, soporte técnico y mantenimiento del sistema.

Convenciones usadas en los ejemplos:

- `t_costura` es un **tiempo unitario en segundos**.
- `cantidad` o `cantidad_asignada` son piezas, no segundos.
- `tiempo_total_segundos = cantidad × t_costura`.
- La UI del administrador convierte el total a minutos con `Math.ceil(segundos / 60)`. Es redondeo hacia arriba al minuto entero, no una conversión de la métrica almacenada.
- Los códigos mostrados son ejemplos. No contienen credenciales ni datos de conexión.

## 4. Regla de búsqueda de tiempo por familia

La regla compartida se encuentra en `lib/productosTiempos.ts` como `tiempoCosturaPorPrefijoSql(aliasProducto)`.

### Pasos de la búsqueda

1. Lee `producto` del registro de orden o asignación.
2. Quita espacios externos y comillas simples o dobles que puedan venir alrededor del código.
3. Obtiene los primeros siete caracteres. Por ejemplo, `155-20000-DGY` produce `155-200`.
4. Busca códigos de `productos_tiempos` cuyo comienzo coincida con ese prefijo. Acepta variantes con comillas iniciales.
5. Descarta `t_costura` nulo o igual a cero, y descarta una actividad `costura` vacía, `N/A`, `NA` o `N/D`.
6. Ordena primero el código base de siete caracteres; luego la variante más corta y finalmente el menor `id`.
7. Devuelve un único `t_costura`, que permanece en segundos.

Esto evita que una variante de la familia con tiempo cero gane a otra variante que sí contiene una métrica válida.

### Validación que debe considerarse en peticiones

Hay una diferencia actual entre rutas: la subconsulta compartida filtra explícitamente `N/A`, `NA` y `N/D`; el `POST /api/productos/peticiones` y el resolvedor ejecutado por su `GET` verifican `t_costura > 0` y que `costura` no sea nulo ni vacío, pero no excluyen esos literales. Si un registro tiene `costura = 'N/A'` y un tiempo positivo, la petición podría quedar marcada como atendida aunque la subconsulta de la orden ignore ese registro. Mantén estos campos limpios y, al modificar el comportamiento, conviene compartir la misma regla SQL entre rutas.

### Ejemplo numérico de extremo a extremo

Producto solicitado: `155-20000-DGY`; cantidad: `9`; métrica válida de familia: `2100` segundos por pieza.

```text
familia                    = primeros 7 caracteres = "155-200"
tiempo unitario            = 2100 segundos/pieza
tiempo total                = 9 piezas × 2100 = 18 900 segundos
tiempo total para mostrar  = ceil(18 900 / 60) = 315 minutos
equivalencia legible        = 5 horas y 15 minutos
umbral del turno            = 480 minutos = 28 800 segundos
resultado                  = no excede 480 minutos
```

Con 64 piezas y el mismo estándar, el total sería `134 400` segundos, `2 240` minutos o `37 h 20 min`; la UI mostraría `2240 min` y la etiqueta `+ 8 Horas`.

La pantalla no debe multiplicar un dato ya convertido a minutos. El contrato del API entrega el estándar en segundos; la conversión se realiza en la presentación.

### Fragmento conceptual para consultar una familia

Este ejemplo ayuda a inspeccionar los datos; la aplicación usa la subconsulta centralizada y aplica también el orden de preferencia.

```sql
SELECT id, cod_proceso, costura, t_costura
FROM productos_tiempos
WHERE cod_proceso LIKE '155-200%'
  AND t_costura > 0
  AND costura IS NOT NULL
  AND TRIM(CAST(costura AS CHAR)) <> ''
  AND UPPER(TRIM(CAST(costura AS CHAR))) NOT IN ('N/A', 'NA', 'N/D')
ORDER BY CHAR_LENGTH(TRIM(cod_proceso)), id;
```

Al ejecutar manualmente una consulta, considera también posibles comillas iniciales en `cod_proceso`; el helper de la aplicación sí contempla esa normalización al comparar.

## 5. Flujo de una petición de tiempo

### Caso A: no hay métrica válida

1. En `app/admin_costura/asignar_orden/page.tsx`, el usuario pulsa **Solicitar tiempo** para una orden sin `tiempo_base`.
2. La página envía a `POST /api/productos/peticiones` el código, OP y descripción. El servidor deriva `modelo` del prefijo de siete caracteres; no confía en un prefijo distinto enviado por el cliente.
3. La API abre una transacción y busca un tiempo positivo en la familia.
4. Si no encuentra candidato, inserta la petición con estatus `pendiente` y responde con `pendiente: true`.
5. La tarjeta aparece en `app/admin/subir_tiempos/page.tsx` dentro de la lista de peticiones.
6. Administración pulsa **Asignar Tiempo**; la API `GET /api/productos/buscar_modelo` intenta completar datos por código/familia y la interfaz presenta los campos editables.
7. `POST /api/productos/peticiones/aprobar` guarda o actualiza el registro en `productos_tiempos` y cambia la petición a `atendido`.

### Caso B: sí hay métrica en la familia

`POST /api/productos/peticiones` crea o actualiza el producto solicitado usando `costura` y `t_costura` de la variante válida. La petición queda `atendido` y la respuesta incluye `asignadoAutomaticamente: true`, `tiempo` y `familia`. La tabla de órdenes actualiza su estado local para mostrar el estimado sin esperar otra navegación.

### Historial

`GET /api/productos/peticiones` devuelve solo pendientes por defecto. Con `?history=1`, incluye todos los estados y calcula `tiempo_asignado` para la tarjeta del historial. La vista administrativa usa ese modo para mostrar **Pendiente**, **Atendida** o **Rechazada**.

## 6. Autoasignación, prioridades y capacidad

Al abrir la página de órdenes cortadas, el cliente llama `POST /api/admin_costura/auto_asignar` y después carga los resultados. El servidor ejecuta la distribución dentro de una transacción.

- Solo considera operadores de tipo `operador` cuya disponibilidad siga vigente.
- Usa `28 800` segundos como capacidad de referencia de ocho horas.
- Toma en cuenta las asignaciones activas; una persona con asignación activa queda ocupada para una segunda tarea hasta liberar su turno o reanudar una pausa.
- Reanuda las asignaciones pausadas antes de repartir más trabajo, cuando existe capacidad.
- Ordena las órdenes por prioridad configurada y antigüedad del registro.
- Reparte piezas de forma iterativa entre operadores que tengan capacidad.
- Puede pausar una tarea normal para atender una orden de prefijo prioritario; al liberar capacidad, la tarea pausada puede reanudarse completa o parcialmente.
- Actualiza el estado del corte a `asignado` o `asignacion parcial` según las piezas que queden.

La lista de prefijos prioritarios está actualmente duplicada en `app/admin_costura/asignar_orden/page.tsx`, `app/operador/page.tsx` y `app/api/admin_costura/auto_asignar/route.ts`. Al modificarla, actualiza las tres ubicaciones para que la etiqueta visual y la regla del servidor no diverjan.

### Cálculo de capacidad del reparto manual

`POST /api/admin_costura/asignar` recibe `{ "orden_id": 123 }`, calcula las piezas que faltan y usa los segundos libres para determinar capacidad por operador. Este endpoint no es el mismo que el ciclo automático `auto_asignar`.

## 8. Paginación y búsqueda en cliente

`lib/pagination.ts` define un tamaño predeterminado de 50 filas y un máximo de 100. `lib/usePaginatedApi.ts` solicita `page` y `pageSize`, agrega resultados al usar **Cargar siguientes 50** y lee `pagination.hasMore`.

El filtro de **Catálogo editable** se ejecuta en el navegador sobre `productos`, es decir, sobre las páginas ya cargadas. Para encontrar un código fuera de las páginas cargadas, agrega más páginas con el botón antes de concluir que no existe.

Al desarrollar un endpoint paginado:

1. Lee los parámetros con `readPageParams(request)`.
2. Solicita `pageSize + 1` filas para detectar si hay otra página.
3. Devuelve `pageRows(rows, pageSize)` y `pageMetadata(page, pageSize, rows.length)`.
4. Ordena de forma estable para que una página no repita ni pierda filas entre solicitudes.

## 9. Importación del catálogo de tiempos

La ruta `app/api/productos/subir-tiempos/route.ts` lee la primera hoja del archivo con SheetJS, normaliza encabezados a minúsculas y acepta dos esquemas.

### Esquema completo

Incluye todos estos encabezados para que se reconozca como carga completa:

```text
id_proceso,cod_proceso,descripcion,costura,t_costura,tapizado,t_tapizado,
armado,t_armado,montado,t_montado,empaque,t_empaque,corte,t_corte
```

Los valores `t_*` son numéricos y están en segundos. Puedes dejar celdas de otras operaciones vacías cuando no correspondan.

### Esquema compacto

Si no se detectan todos los encabezados completos, la API intenta el esquema alternativo:

```text
codigo,nombre_secundario,costura,tiempo
```

En este formato, `tiempo` alimenta `t_costura` y también se interpreta como segundos por pieza. La descripción se obtiene de `nombre_secundario` o, como alternativa, de `nombre`.

Las filas sin código se omiten. Códigos repetidos dentro del archivo se consolidan; en métricas repetidas conserva el mayor tiempo y se usa una transacción para guardar lotes de hasta 200 productos. La escritura usa `ON DUPLICATE KEY UPDATE`, por lo que una carga puede modificar datos existentes: valida el archivo antes de subirlo.

## 10. Validación y consistencia

- `lib/productosTiempos.ts` centraliza la lectura familiar usada por las consultas de órdenes y operador.
- `app/api/productos/crud/route.ts` valida que las métricas sean numéricas y mayores o iguales a cero; las celdas vacías se convierten a `NULL`.
- Una métrica de cero puede guardarse en catálogo, pero no se considera un tiempo disponible en la subconsulta compartida.
- Las modificaciones de filas usan el ID como identidad. Cambiar `cod_proceso` puede converger con otro código; el endpoint debe manejar la fusión transaccional y la restricción única.
- Los cambios que alteren prefijos, selección de variantes, unidades o límites de turno requieren revisar todas las pantallas que muestran o consumen tiempos.
- Las sesiones reales se miden con diferencias de fecha en MySQL (`TIMESTAMPDIFF(SECOND, ...)`) y se acumulan en `tiempo_segundos`.

## 11. Actualizaciones en vivo

`server.mjs` integra Socket.IO con el servidor web y define rutas que notifican cambios. `components/RealtimeProvider.tsx` instala el cliente; `lib/useRealtimeRefresh.ts` escucha `app:data-changed`, agrupa eventos cercanos y llama la función de recarga de la pantalla.

Al añadir una mutación:

1. Confirma si la ruta ya está registrada entre las rutas que notifican.
2. Si la mutación afecta una tabla visible en vivo, emite la notificación tras completarla.
3. En la página, usa `useRealtimeRefresh` con una función estable que recargue las consultas necesarias.
4. Asegura que los estados locales optimistas se reconcilien con la respuesta del servidor.

Cuando cambie el producto:
